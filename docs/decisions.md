# 設計上の決定と背景

## コア層は DB 非依存に保つ
メタデータ変換ロジックは特定の DWH に依存しない純粋な Python として実装し、
接続とSQL方言の差異はアダプタ層に閉じる。
これにより、Postgres で開発して他プラットフォームで検証する際に
接続設定の差し替えだけで済み、テストも DB なしで実行できる。

## 開発環境に PostgreSQL を採用する
AutomateDV は v0.9.7 で Postgres を正式サポートしている。
無料であり、CI でもサービスコンテナとして起動できる。

### DuckDB を採用しない理由
軽量だが AutomateDV の公式サポート対象外。
マクロがプラットフォームごとに分岐しているため、動作の保証がない。

## バージョンは最新を追わない
AutomateDV の公式互換表を基準にする。

| 対象 | 固定 | 根拠 |
|---|---|---|
| Python | 3.12 | dbt-postgres での 3.13 サポートは dbt-core 1.10 以降 |
| dbt-core / dbt-postgres | 1.10.x | AutomateDV v0.11.4 の推奨。1.11 / 1.12 は未検証 |
| AutomateDV | 0.11.4 以上を明示ピン | https://automate-dv.readthedocs.io/en/latest/versions/ |
| dbt_utils | 1.4.1 | 必要 dbt バージョンは `>=1.3.0, <3.0.0` |

バージョンを上げる際は、必ず上記互換表を再確認する。

## 開発フロー
main を保護し、feature ブランチから PR 経由で squash merge する。
- ブランチ: `feat/` `fix/` `docs/` `chore/` `test/`
- コミット: Conventional Commits
- CI: PR ごとに Postgres コンテナを起動し `dbt build` と `pytest` を実行する

## テストデータ
公開データセット（jaffle_shop, TPC-H）は使用しない。
いずれも変更履歴を持たないため、Satellite の hashdiff による差分検知と
インクリメンタルロードの正しさを検証できない。
Faker で生成し、乱数シードを固定して再現性を確保する。

## ローカル開発環境（2026-08-12）

### dbt の実行場所：ホスト（WSL2）の uv 管理 venv。コンテナは PostgreSQL のみ

dbt をコンテナに入れると実行のたびにコンテナ越しになり、反復速度と
エディタの補完・デバッガの利便性が落ちる。また GitHub Actions では
`services:` で PostgreSQL を起動する構成になるため、
「DB のみコンテナ・dbt はホスト」がローカルと CI で同一構成になる。

トレードオフとして環境まるごとの再現性は下がるが、
`uv.lock` と `.python-version` の固定で実用上の差は小さいと判断した。

### PostgreSQL：16-alpine / ホスト側公開ポート 5433

5432 は Windows 側に PostgreSQL がインストールされている場合に競合するため、
ホスト側のみ 5433 にずらしている。コンテナ内は 5432 のまま。

データ領域は named volume（`pgdata`）を使用。
WSL2 でバインドマウントを使うと I/O 性能が落ち、権限エラーも起きやすい。

### dbt プロジェクトの位置：リポジトリ直下ではなく `dbt/`

Python パッケージと dbt プロジェクトが同居するため、直下は Python 側に譲る。

### dbt の実行方法：リポジトリ直下から Makefile 経由で実行する

`dbt/` 配下に置く構成のため、実行時は
`--project-dir dbt --profiles-dir dbt` の指定が必要になる。
これらは dbt 1.5 以降のサブコマンド側オプションであり、
`dbt build --project-dir dbt` のようにサブコマンドの後ろに置く。
指定漏れを防ぐため、コマンドは Makefile に集約し、
**リポジトリ直下から `make` で実行することを標準とする。**

`cd dbt` して直接 `dbt` を叩く方法も動作するが、標準としない。
GitHub Actions では Makefile のターゲットをそのまま呼び出す構成にできるため、
ローカルと CI で実行コマンドを一致させられることを優先した。
実行方法が2通り存在すると、CI 固有の失敗を切り分ける際に
「ローカルでは通るのに CI だけ落ちる」の原因になる。

主なターゲット:

| コマンド | 内容 |
|---|---|
| `make up` / `make down` | PostgreSQL コンテナの起動・停止 |
| `make deps` | dbt パッケージの取得 |
| `make build` | 全モデルの build |
| `make build SELECT=+stg_crm_customer` | 対象を絞った build |
| `make parse` | 依存解決のみ確認（build 前の切り分け） |
| `make show SQL="..."` | インラインクエリの実行 |
| `make compiled MODEL=...` | 生成された SQL の表示 |
| `make psql` | コンテナ内 psql への接続 |

Makefile のインデントはタブ必須のため、`.editorconfig` で
`[Makefile] indent_style = tab` を指定している。

### profiles.yml：`~/.dbt/` ではなくリポジトリ内に配置

環境変数のデフォルト値を持たせてあり、`.env` が無くても動作する。
CI では `POSTGRES_PORT` 等を環境変数で上書きするだけで同じファイルを使える。

### AutomateDV：0.11.4 に完全固定し package-lock.yml をコミット

AutomateDV 0.11.4 の対応 dbt は `>=1.9.x, <3.0.0` だが、
推奨は「最新の dbt 1.10.x」。0.11.3 以前は 1.9.x 推奨のため、
dbt 1.10 系を使う場合は 0.11.4 以上が必要。
出典: https://automate-dv.readthedocs.io/en/latest/versions/

CI の安定を優先し、範囲指定ではなくバージョン完全固定とする。

### 認証情報の扱い

`.env.example` にはローカル使い捨て DB の初期値を実値で記載している。
コンテナ内にのみ存在し `docker compose down -v` で消えるため、
公開リポジトリに含めて問題ないと判断した。

Snowflake 対応を追加する時点でこの方針は変更する。
外部サービスの認証情報は `.env.example` に変数名のみを記載し、値は空とする。

### 検証結果（2026-08-12）

- dbt 1.10.22 / dbt-postgres 1.10.2 / AutomateDV 0.11.4
- `make debug` の Connection test: OK
- `make run`（モデル 0 本）: 正常終了、`Found 867 macros`

## ステージング層の実装（2026-08-15）

### ハッシュアルゴリズム：SHA-256（`vars: hash: sha`）

Data Vault Alliance の推奨は SHA-1 だが、AutomateDV では Postgres で
SHA-1 を利用できない。完全な実装に pgcrypto 拡張を要するためである。
残る選択肢は MD5 と SHA-256 で、将来 Snowflake 等のアダプタを追加した際に
同一の設定をそのまま使い回せる SHA-256 を採用した。

ストレージは MD5 の 16 バイトに対し 32 バイトとなるが、
本プロジェクトのデータ規模では無視できる差である。

ロード済みデータがある状態でアルゴリズムを変更すると full-refresh が必要になるため、
Hub を作成する前のこの時点で確定させた。
出典: https://automate-dv.readthedocs.io/en/latest/best_practises/hashing/

### ハッシュキーの型：BYTEA

Postgres では MD5 / SHA-256 のいずれも BYTEA 型で出力される。
目視確認する際は `encode(customer_hk, 'hex')` を用いる。

### `LOAD_DATETIME` の供給元：ソース側の取り込み時刻カラム

`CURRENT_TIMESTAMP` を用いると実行のたびに値が変わり、
日次スナップショット7日分の検証と CI の再現性が失われる。
ランディング層（seed）に `crm_ingested_at` を持たせ、
`derived_columns` で `LOAD_DATETIME` にマッピングする。

AutomateDV 公式チュートリアルも同様に、
ソース側の取り込み時刻カラムから `LOAD_DATETIME` を派生させる構成を採っている。

### `RECORD_SOURCE`：ソーステーブル識別子

公式例は定数 `1` を用いているが、連番では監査時にソースを特定できず、
番号とシステムの対応表を別途管理することになる。
`crm_customer` のようなソーステーブル識別子を用いる。

ソースを追加した後に変更すると既存の Satellite の値と不整合になるため、
命名規則は最初のソース実装時点で確定させる。

### ビジネスキーの正規化：数字部分を抽出し4桁ゼロ埋め

同一顧客がソースごとに異なるキー形式（CRM は `CUST0001`、基幹は `C-0001`）を
持つ設計としているため、ステージング層で共通形式に収束させる。
これを行わない場合、同一顧客が異なるハッシュ値を持ち Hub に重複行が発生する。

処理は DV2.0 のハードルールに該当するため、ステージング層で行い
Raw Vault 側では一切変換しない。

### 正規化後のカラム名：`CUSTOMER_BK`

ソース側の生カラム名（`customer_id` / `customer_code`）と衝突せず、
全ソースで共通の名前を使える。AutomateDV の `derived_columns` は
ソースと同名のカラムを定義すると値を上書きするため、
別名にすることで生の値も監査用に残せる。

DV の慣例では Hub の自然キーカラムは業務名を用いることが多く、その点では外れるが、
2ソースで生カラム名が異なる以上、共通名の定義は不可避と判断した。

### 識別子のエスケープ機能は有効にしない

Postgres は未クォートの識別子を小文字に畳む。
AutomateDV のエスケープ機能を有効にすると識別子が大文字で固定され、
以降のすべてのクエリでダブルクォートが必要になる。

メタデータ YAML には可読性のため大文字で記述するが、
実際に生成されるカラムは小文字（`customer_hk` 等）となる。

## テスト方針

### ステージング層のテストは必須とする

ビジネスキー正規化の不具合は Raw Vault 側からは検知できない。
Hub や Satellite を見ても「そういうデータである」としか判別できないためである。

実装時に実際に発生した不具合は以下の3種で、
いずれもステージング層のテストでのみ検知できる。

| 不具合 | 結果 | 検知手段 |
|---|---|---|
| 正規化前のキーをハッシュした | 同一顧客が別エンティティになる | 複数ソース投入後の Hub 件数 |
| 正規化式の誤りでキーが潰れた | 全顧客が同一エンティティになる | `unique` |
| `LPAD` が入力を無言で切り捨てた | 別顧客と衝突する | 入力前提の検証（後述） |

### 「出力形式の検証」と「入力前提の検証」を分けて置く

`LPAD` は入力が指定長を超えた場合、エラーを出さずに切り捨てる。
たとえば 5 桁の顧客番号 `CUST12345` は `1234` となるが、
これは「4桁の数字」であるため出力形式の検証を通過してしまう。

したがって、以下の2種を必ず組で置く。

- 出力形式の検証：`customer_bk` が4桁の数字であること（カラムレベル）
- 入力前提の検証：正規化前の桁数が想定長を超えないこと（モデルレベル）

### テストは「意図どおり落ちること」を確認する

テストを追加した際は、検知対象の不具合をデータに意図的に混入させ、
該当するテストのみが FAIL することを確認する。
通過しているだけのテストは、何も検証していない可能性を排除できない。

### `dbt_utils` のテスト引数は `arguments:` の下にネストする

dbt Core 1.10.6 以降および dbt Fusion では、
テスト引数を `arguments:` キーの下にネストする形式が必須となる。
公開されている解説記事の多くは旧形式のため、そのまま転記すると動作しない。

### `ERROR` と `FAIL` を区別する

- `ERROR`：テスト SQL 自体が実行できなかった（設定・スキーマの問題）
- `FAIL`：SQL は正常に実行され、データが条件を満たさなかった

`ERROR` の場合、そのテストはデータについて何も検証していない。
CI のログではこの2つを区別して扱う。

## 既知の制約

- ビジネスキー正規化の SQL（`REGEXP_REPLACE` / `LPAD`）は PostgreSQL 方言に依存する。
  将来のアダプタ層で吸収する対象
- `LPAD` の桁数は現在4桁固定。桁数を広げても切り捨ての性質は変わらないため、
  桁の拡張ではなく入力前提の検証テストで担保する方針とする

## デバッグ手順

### AutomateDV が生成した SQL を確認する

メタデータ駆動のパッケージでは、
「YAML はエラーにならないが意図と異なる SQL が生成される」が最も多い失敗形態である。
モデルの挙動が想定と異なる場合、まず生成された SQL を確認する。

### メタデータ YAML にバックスラッシュを含む正規表現は書けない

SQL 式にシングルクォートが含まれるため YAML 値はダブルクォートで囲むことになり、
その結果 YAML がエスケープシーケンスを解釈する。
`\d` `\D` 等は使用できないため、`[^0-9]` のような表記を用いる。

### `REGEXP_REPLACE` は第4引数 `'g'` が必須

省略すると最初の1箇所のみ置換される。

### クエリによる確認は `dbt show --inline` を用いる

`profiles.yml` の接続情報をそのまま使うため、
ローカルに psql クライアントを追加せずに結果を確認できる。CI でも同様に利用可能。

探索的な確認やメタコマンドが必要な場合は `make psql` を用いる。
コンテナ内から接続するため、ポートは 5432（公開ポート 5433 ではない）となる。

### build 前に依存解決を確認する

モデル追加時やパッケージ更新後は、先に依存解決だけを確認すると
SQL の問題と設定の問題を切り分けやすい。
